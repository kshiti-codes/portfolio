4Step-by-Step Data Flow
1
User Opens App → WebSocket Connection
User A opens the app. The client establishes a WebSocket connection to a Chat Server. This is a persistent TCP connection — not HTTP. The server registers User A's connection in Redis as user_id → server_id + socket_id. This is also how "online presence" is tracked (key with TTL = last heartbeat).
WebSocket Redis
2
User A Sends a Message
User A types a message and hits send. The client sends it over the WebSocket to Chat Server 1. The server assigns it a unique message_id (using a Snowflake ID or UUID). The message is immediately written to Cassandra with the conversation_id as the partition key — ensuring all messages in a conversation are co-located. The server sends back a SENT receipt to User A (one checkmark ✓).
Cassandra Snowflake ID
3
Routing to User B (Cross-Server)
Chat Server 1 looks up User B's location in Redis: "User B is connected to Chat Server 3." Server 1 publishes the message to Redis Pub/Sub on the channel user:B. Chat Server 3 is subscribed to that channel, receives the message, and pushes it over User B's WebSocket connection. User B sees the message instantly. Server sends DELIVERED receipt back (double checkmark ✓✓).
Redis Pub/Sub WebSocket
4
User B is Offline → Push Notification
If User B is NOT in Redis (offline), Chat Server 1 publishes the message to Kafka. A Notification Service consumes from Kafka and calls APNs (Apple) or FCM (Android) to deliver a push notification. The message is still stored in Cassandra — User B will fetch missed messages when they come back online via the REST API.
Kafka APNs / FCM
5
User B Opens App → Syncs Missed Messages
User B reconnects. Client sends the last_seen_message_id to the server. The server queries Cassandra: SELECT * FROM messages WHERE conversation_id=X AND message_id > last_seen_id. All missed messages are returned in order. Once B reads the message, a READ receipt event is sent back over WebSocket to User A (blue checkmarks 🔵).
Cassandra WebSocket
6
Media Upload (Images / Files)
For media, the client directly uploads to S3 using a pre-signed URL (server generates it, but bytes never go through your app server). The S3 URL is sent as the message content. On receive, clients download from CDN (CloudFront), not from S3 directly. This keeps bandwidth off your servers entirely.
S3 CDN
5Key Components
🔌
WebSocket Servers (Stateful)
Each server maintains persistent connections with a set of users. Unlike REST servers, these are stateful — you can't route any request to any server; each user must always hit THEIR server.
→ Consistent hashing routes users to the same server. If a server dies, clients reconnect and Redis re-registers them on a new server.
🔄
Redis (Pub/Sub + Presence)
Two jobs: (1) Routes messages between chat servers via pub/sub channels. (2) Tracks who is online via user_id → server_id with heartbeat TTLs.
→ In-memory = microsecond lookups. Presence must be checked on EVERY message send — it cannot be slow.
🗄️
Cassandra (Message Store)
Stores all messages. Schema: partition key = conversation_id, clustering key = message_id DESC. This ensures all messages for a chat are on the same node and sorted by time.
→ Cassandra is designed for high write throughput and time-ordered data. PostgreSQL would buckle under billions of inserts/day.
📨
Kafka (Async Events)
Receives message events for async processing: offline notifications, analytics, message search indexing. Decouples the critical write path from all secondary concerns.
→ Never do heavy work synchronously in the hot path. Kafka buffers it and workers process at their own pace.

7Scaling Strategy
⚖️
Scale WebSocket Servers Horizontally
Use consistent hashing to route each user to a specific server. Each server handles ~100K concurrent connections. Add servers as load grows. Redis stores the routing table.
🔀
Cassandra Horizontal Sharding
Cassandra natively shards by partition key (conversation_id). Add more nodes and Cassandra redistributes data automatically. Scales to billions of messages with no schema changes.
🌍
Multi-Region Deployment
Deploy WebSocket servers and Cassandra in every region. Users connect to nearest region. Cross-region messages route through Kafka. Cassandra supports multi-datacenter replication natively.
8Interview Gold 🏆
⚡ Say These in Your Interview
!
Message ordering: Never use wall-clock timestamps for ordering — clock skew between servers causes issues. Use a Lamport clock or Snowflake ID (timestamp + server ID + sequence) which is globally monotonically increasing.
!
Why Cassandra over PostgreSQL for messages: PostgreSQL does ~10K writes/sec. Cassandra does 1M+ writes/sec. At WhatsApp scale (50B msgs/day), there's no choice. Also Cassandra's partition key = conversation_id means range scans are O(1) per conversation.
!
End-to-end encryption: Each user has a public/private key pair. Private key stored ONLY on device. Messages encrypted with recipient's public key before sending. Server stores only ciphertext — even WhatsApp can't read your messages.
!
Group chat fan-out problem: If a group has 1000 members, one message = 1000 WebSocket writes + 1000 Cassandra writes. Solution: store one copy of the message, each member has a pointer to it (not a copy). Only send the message_id in WebSocket fan-out.
!
The exactly-once delivery illusion: Networks are unreliable — message can be sent twice on retry. Use idempotency keys (client-generated UUID per message). Server checks if message_id already exists before writing.

4Step-by-Step Data Flow
1
User Creates a Post
User submits post. Post Service validates, saves the post to Cassandra (the raw post lives here forever), and uploads any media directly to S3 via pre-signed URL. Post gets a unique post_id (Snowflake ID). Service publishes a post.created event to Kafka.
KafkaCassandraS3
2
Fan-out Service Distributes the Post
The Fan-out Service consumes the Kafka event. It fetches the author's follower list from PostgreSQL. For each follower, it PREPENDS the new post_id into that user's feed list in Redis (a sorted set or list capped at 500 items). This is the push model (fan-out-on-write).
RedisPostgreSQL
3
Celebrity Exception (Pull Model)
If the author has >1M followers, pushing to 1M Redis keys for ONE post is too slow. Solution: skip the fan-out for celebrities. When a user loads their feed, the Feed Service fetches posts from celebrities they follow directly from Cassandra and merges them with their pre-computed feed from Redis. This is the hybrid model.
CassandraRedis
4
User Reads Their Feed
User opens the app and requests their home feed. Feed Service reads the user's post_id list from Redis (fast, already sorted). It batch-fetches the actual post data for those IDs from Cassandra. CDN URLs for images are served directly — never through the app server. Response is paginated using cursor-based pagination.
RedisCassandraCDN
5
Likes, Comments, Engagement
Like events go to Redis counter (INCR) for real-time counts, and also queued in Kafka for async persistence to Cassandra. Never write every like directly to the database — aggregate in Redis, flush to DB every 30 seconds in batch. Comments stored in Cassandra with post_id as partition key.
Redis CounterKafka
6
Search and Trending
Every post is also indexed into Elasticsearch by the fan-out service. Trending topics computed using a Redis sorted set — hashtag mentions are INCRed with a sliding window TTL. Top-10 trending = ZREVRANGE in O(log N).
ElasticsearchRedis Sorted Set

6Interview Gold 🏆
⚡ Say These in Your Interview
!
The fan-out dilemma: Push (fan-out-on-write) = fast reads, slow writes. Pull (fan-out-on-read) = slow reads, fast writes. The answer is hybrid: push for regular users, pull for celebrities. The interviewer is testing if you know this.
!
Cursor vs Offset pagination: Never use OFFSET 100 for feeds. If 5 new posts appear, offset shifts and you skip/repeat items. Use cursor = last_seen_post_id. This is stable regardless of insertions.
!
Like counts don't need to be exact: "1.2M likes" is fine. Use Redis INCR (fast, atomic) and flush to DB in batches. No need for a DB write on every like — that's a classic bottleneck interview answer.
!
Feed ranking vs chronological: A pure time-sorted feed is easy. A ranked feed (like Facebook/Instagram) involves a ML scoring model. Pre-compute scores offline using Spark, store ranked post_id list in Redis per user. Refresh every 15 minutes.

3Step-by-Step Data Flow
1
Creator Uploads Video
Client requests a pre-signed S3 URL from the Upload Service. The client uploads the raw video file DIRECTLY to S3 — your servers never touch the bytes (crucial for scalability). After upload completes, S3 triggers an event (or the client notifies your API) and a upload.completed event goes to Kafka.
2
Transcoding Pipeline (DAG)
A Transcoder Worker fleet picks up the Kafka event. Each worker downloads the raw video from S3 and uses FFmpeg to transcode into multiple resolutions: 360p, 480p, 720p, 1080p, 4K. Each resolution is split into 2-10 second chunks in HLS format (.m3u8 manifest + .ts chunk files). A thumbnail is extracted. All outputs uploaded back to a separate S3 bucket (processed). This is a DAG pipeline: transcode → thumbnail → metadata → index.
3
CDN Distribution
Processed S3 is the origin. CDN (CloudFront/Akamai) has 200+ edge nodes globally. First request to each edge = CDN fetches from S3 origin and caches. All subsequent requests served from nearest edge node. This is why Netflix can serve 250M users — their origin only handles a tiny fraction of traffic.
4
Viewer Requests Playback
Viewer clicks play. Video API checks Redis for cached video metadata (title, description, available resolutions, CDN URL of .m3u8 manifest). On cache miss, fetches from PostgreSQL and caches. Returns the manifest URL pointing to the CDN. Video player downloads the .m3u8 manifest from CDN, which lists all chunk URLs.
5
Adaptive Bitrate Streaming (ABR)
The video player monitors the viewer's network bandwidth every second. If buffer is healthy → request higher quality chunks (1080p). If buffer is low → drop to 480p. The player fetches chunks from CDN autonomously — your servers are not involved at all during playback. This is the beauty of HLS: the player drives quality, not the server.
6
View Count, Watch History, Recommendations
Every view event goes to Kafka. A View Counter service uses Redis HyperLogLog to count approximate unique viewers (±0.81% error, uses only 12KB memory vs millions of user IDs). Watch position saved to Redis every 15 seconds, flushed to Cassandra on exit. Recommendation signals fed into ML pipeline via Kafka → Spark → vector store.

5Interview Gold 🏆
⚡ Say These in Your Interview
!
Why chunked video? If you stream a 2GB file, the user waits for the whole thing. With 2-second chunks, playback starts after downloading just the first chunk (~1MB). The player pre-buffers the next few chunks while playing.
!
Transcoding bottleneck: A 1-hour video takes ~20 minutes to transcode at full quality. To parallelize: split video into 1-minute segments, transcode all segments in parallel across a GPU worker fleet, then reassemble. YouTube does this.
!
CDN cache hit rate: Popular videos have 99%+ CDN cache hits. Long-tail videos (rarely watched) often miss the CDN — that's fine because they have few viewers. The CDN economics work because top 1% of videos get 99% of traffic.
!
HyperLogLog for view counts: Storing 1M user IDs to count unique viewers uses 8MB. HyperLogLog counts 1B unique items using only 12KB with 0.81% error. At YouTube scale, this is the only sane approach.

Ride Sharing App
e.g. Uber · Lyft · Ola · Bolt · DoorDash
LOCATION REAL-TIME MATCHING
1Requirements

Functional

  • Rider requests a ride from A to B
  • Find nearby available drivers
  • Match rider to nearest driver
  • Real-time driver location on map
  • Price estimation before booking
  • Trip history, ratings, payments

Non-Functional

  • Driver location updated every 4 seconds
  • Match found in <1 second
  • System handles 1M concurrent drivers
  • Low latency for location reads (<10ms)
  • ACID for payments
2Step-by-Step Data Flow
1
Driver Goes Online → Location Updates
Driver opens app and goes "available." Driver app sends GPS coordinates every 4 seconds via HTTP or WebSocket to the Location Service. The service stores the driver's location in Redis using the GEOADD command: GEOADD drivers:available longitude latitude driver_id. Redis stores this as a geospatial index using GeoHash internally. Old location automatically expires (TTL = 30s) — driver is considered offline if no update received.
Redis GEOKafka
2
Rider Requests a Ride
Rider opens app, drops a pin for pickup. Ride Service receives the request with pickup lat/lng. It calls: GEORADIUS drivers:available <lng> <lat> 5 km in Redis — returns list of available driver IDs within 5km radius, sorted by distance. This is an O(N+log M) operation, incredibly fast. A trip record is created in PostgreSQL with status = MATCHING.
Redis GEORADIUSPostgreSQL
3
Driver Matching
The Matching Service gets the candidate drivers list. It picks the nearest driver and sends them a ride request notification (via WebSocket/push). The driver has 15 seconds to accept. If rejected or timeout, the next closest driver is tried. This is done with a sequential offer strategy (not broadcast to all). The winning driver_id is locked in Redis to prevent double-assignment: SET trip:{id}:driver {driver_id} NX EX 300.
Redis NX LockWebSocket
4
Real-Time Trip Tracking
Once matched, driver app continues sending location every 4 seconds. Now these updates go to a trip-specific Kafka topic. A stream processor pushes each location update via WebSocket to the rider's app. Rider sees the driver moving on the map in real-time. Location events also go into the Kafka stream for surge pricing calculations and analytics.
KafkaWebSocket
5
Price Calculation (Surge Pricing)
A Pricing Service consumes demand signals from Kafka: ride requests per city zone per minute vs available drivers per zone. Zones are defined by H3 hexagonal grids (Uber's open-source tool). Surge multiplier = demand/supply ratio. Stored in Redis per H3 cell with 1-minute TTL. Price = base fare × surge × distance (from Google Maps Distance Matrix API).
H3 GeoIndexGoogle Maps API
6
Trip Completion & Payment
Driver marks trip complete. Trip status → COMPLETED in PostgreSQL. Final route traced from stored GPS points (Cassandra/Kafka). Total distance calculated → final fare computed. Payment charge via Stripe API. Receipt emailed. Driver earnings credited to wallet. Ratings and reviews stored. All post-trip work is async via Kafka consumers — doesn't block the driver.
PostgreSQLStripeKafka

4Interview Gold 🏆
⚡ Say These in Your Interview
!
Why GeoHash/Redis GEO instead of Postgres? PostgreSQL with PostGIS can do spatial queries but requires a full index scan and is slow at high write rates (1M driver updates/4s = 250K writes/sec). Redis GEO operations are O(N+log M) in memory — orders of magnitude faster.
!
H3 hexagonal indexing: Uber open-sourced H3 — divides the globe into hexagonal cells at multiple resolutions. Hexagons tesselate without distortion unlike squares. This allows perfect zone-based surge pricing and driver allocation.
!
Preventing double-matching: When two ride requests come in simultaneously for the same driver, use a Redis distributed lock (SET NX EX = Set if Not eXists with expiry). First request gets the lock, second gets rejected and tries next driver.
!
Why save GPS to Kafka not direct DB? At 250K GPS updates/second, no database can handle direct writes. Kafka buffers all events. A consumer batch-writes to Cassandra (time-series GPS trail). Only the current location lives in Redis — history in Cassandra.

3Step-by-Step Data Flow
1
User Searches for Products
Search query goes to Elasticsearch — full-text search with filters (price range, rating, category). ES ranks results using BM25 + business signals (sponsored, popular). Product images served directly from CDN. Search results are NOT from the main PostgreSQL — that would be too slow for complex queries.
2
View Product Page
Product Service checks Redis for cached product data. Hit rate ~95% for popular items. On cache miss, fetches from PostgreSQL. Product page also calls Inventory Service to show "In Stock" status — this also comes from Redis (inventory counter), not the DB directly. Product images from CDN.
3
Add to Cart
Cart is stored in Redis as a hash: cart:{session_id} → {product_id: quantity} with a 30-day TTL. No DB write needed for cart. This makes cart operations O(1) and massively reduces DB load. Cart is only persisted to PostgreSQL when user is logged in and order is placed.
4
Checkout — Inventory Reservation
CRITICAL STEP. Before charging the customer, inventory must be reserved. Inventory Service uses a Redis atomic decrement: DECRBY inventory:{product_id} quantity. If result goes below 0 → rollback with INCRBY and return "Out of Stock." This atomic operation prevents overselling without DB-level locks. A reservation record is saved to PostgreSQL with a 15-minute expiry.
5
Payment Processing
Client receives a payment intent from your server. Client submits card details directly to Stripe (PCI compliance — card numbers never touch your servers). Stripe confirms and calls your webhook. Your Payment Service records the payment in PostgreSQL and updates order status. CRITICAL: use an idempotency key on every Stripe API call to prevent double charges on retries.
6
Order Fulfillment (Saga Pattern)
Order placed event goes to Kafka. Multiple consumers: (1) Notification Service → sends confirmation email. (2) Fulfillment Service → updates warehouse. (3) Analytics Service → records sale. If ANY step fails, a compensating transaction (Saga) rolls back: refund payment, restore inventory. This is the distributed transaction pattern for microservices.
4Interview Gold 🏆
⚡ Say These in Your Interview
!
Flash Sale problem: 100K users hit "Buy" simultaneously. If you check inventory in DB under load → DB dies. Solution: pre-load stock into Redis before sale starts. Use Redis DECR atomic ops — Redis processes 1M ops/sec single-threaded, so there's no race condition. Only persist final state to DB.
!
Optimistic vs Pessimistic locking: Pessimistic = lock the inventory row (blocks other requests). Optimistic = read version, attempt update only if version unchanged (retry on conflict). For e-commerce, optimistic locking is preferred for low-contention products. Redis DECR is better for high-contention flash sales.
!
Saga pattern: In microservices, you can't do a 2-phase commit across Order DB + Payment DB + Inventory DB. Instead, each service does its local transaction and publishes events. On failure, compensating transactions undo the work. This is eventual consistency done safely.
!
Why not store cart in DB? A user might add/remove 20 items before checking out. That's 20 writes to a table that holds nothing. Cart is ephemeral session data — Redis with TTL is the perfect fit. DB is reserved for confirmed orders.

File Storage / Cloud Drive

MEDIA HEAVY SYNC VERSIONING
1Requirements

Functional

  • Upload, download, delete files
  • Folder structure, rename, move
  • Sync across devices (auto)
  • Share files/folders with permissions
  • Version history and restore
  • Preview files (images, PDFs, docs)

Non-Functional

  • Files up to 5GB supported
  • Resume interrupted uploads
  • Deduplicate identical files
  • File changes synced in <30 seconds

2Step-by-Step Data Flow
1
File Upload — Chunking
Client splits the file into 4MB chunks. For a 1GB file = 250 chunks. Client computes a SHA-256 hash of each chunk. Client sends the list of chunk hashes to the server. Server checks which chunks it already has. Client only uploads the missing chunks. This enables deduplication (if someone else uploaded the same chunk, you skip it) and resumable uploads (if connection drops, resume from last uploaded chunk).
SHA-256S3 Multipart
2
Upload to Storage
Client gets a pre-signed S3 URL for each missing chunk. Client uploads each chunk directly to S3. Your servers never proxy the bytes. After all chunks uploaded, client calls your API to "finalize" the file. File Service triggers an S3 multipart complete to assemble chunks into the final object.
S3 Pre-signed URL
3
Metadata Storage
File metadata (name, path, size, owner, permissions, version) stored in PostgreSQL. The file content itself is in S3. PostgreSQL stores the mapping: file_id → s3_key. Folder hierarchy modeled as a closure table (each ancestor-descendant pair stored explicitly) — enables fast "get all files in folder" queries without recursive CTEs.
PostgreSQLRedis Cache
4
Cross-Device Sync
When Device A uploads a file, a sync.event goes to Kafka. A Sync Service identifies all other devices of the same user and sends a push notification (WebSocket or long-poll) telling them to sync. Device B wakes up, fetches the metadata change, identifies the new/changed file, and downloads only the changed chunks from CDN.
KafkaWebSocket/Poll
5
Version History
Every time a file is modified, a new version is created in PostgreSQL: file_id + version_number → new_s3_key. Old S3 objects are NOT deleted — moved to S3 Glacier (cold storage, 10x cheaper). User can browse version history and restore any previous version — it's just a pointer update in PostgreSQL.
PostgreSQLS3 Glacier

4Interview Gold 🏆
⚡ Say These in Your Interview
!
Content-Addressable Storage: Store files by their SHA-256 hash, not by name. Two users uploading the same file = one S3 object, two metadata pointers. Dropbox saved petabytes this way — 30% of their files were duplicates.
!
Delta sync: When a user edits a large document, don't re-upload the whole file. Identify which 4MB chunks changed (different hash), upload only those. For a 100MB file where only 2 paragraphs changed, you upload ~4MB instead of 100MB.
!
Conflict resolution in sync: User edits a file on two devices while offline. When both sync: create two copies — file.txt and file (User's conflicted copy 2024-01-01).txt. User decides which to keep. This is Dropbox's approach — simpler than CRDT for files.

Payment / Wallet System
e.g. Stripe · PayPal · Venmo · Google Pay · Razorpay
TRANSACTIONAL ACID IDEMPOTENT
1Step-by-Step Data Flow
1
Initiate Payment — Idempotency First
Client generates a unique idempotency_key (UUID) before making any API call. This key is sent with every request. Server checks Redis: "Have I seen this key before?" If yes, return the SAME response as before. If no, proceed. This ensures that if the network drops and the client retries, they never get double-charged. This is the #1 rule in payment systems.
Redis Idempotency
2
Balance Deduction — ACID Transaction
Payment involves multiple DB operations that must all succeed or all fail: (1) Deduct from sender's balance, (2) Add to receiver's balance, (3) Create a transaction record. All three happen in a single ACID database transaction in PostgreSQL. If any step fails, the entire transaction rolls back. This is why PostgreSQL (not Cassandra, not Redis) handles money — atomicity and consistency are guaranteed.
PostgreSQL ACID
3
Double-Entry Bookkeeping
Every payment creates TWO ledger entries (not one): a DEBIT on the sender's account and a CREDIT on the receiver's account. The sum of all credits must always equal the sum of all debits. This mathematical invariant makes it impossible to "lose" or "create" money. Every financial system since 1400s uses this. Ledger table: account_id, amount (±), type, reference_id, timestamp.
4
Payment to External Provider (Stripe)
For card payments, your server creates a PaymentIntent via Stripe API (never handle card numbers yourself). Client submits card details to Stripe's servers directly. Stripe returns a token. Your server confirms the payment using the token. Stripe calls your webhook when payment succeeds/fails. Store the Stripe payment_intent_id in your DB — this is your external reference for disputes.
Stripe APIWebhook
5
Post-Payment — Async Processing
On successful payment, publish payment.succeeded event to Kafka. Consumers: Notification Service (receipt email/SMS), Fraud Detection Service (analyze patterns), Analytics Service (revenue metrics), Reconciliation Service (daily settlement with bank). None of this blocks the user's payment confirmation.
Kafka
2Interview Gold 🏆
⚡ Say These in Your Interview
!
Why PostgreSQL and not NoSQL for payments? Money requires strong ACID consistency. If two requests read the same balance simultaneously and both deduct, you get negative balance. PostgreSQL's serializable isolation prevents this. Cassandra's eventual consistency means a 0.001% chance of data anomaly — unacceptable when money is involved.
!
Distributed lock for concurrent payments: User has $100, sends $80 to Alice and $80 to Bob simultaneously. Both reads show $100. Both deductions succeed individually. Result: $-60 balance. Solution: SELECT FOR UPDATE in PostgreSQL (pessimistic lock) or Redis Redlock for cross-service locking. Lock the account row before reading.
!
Event sourcing for audit trail: Never UPDATE a payment record — only INSERT new events (payment initiated, captured, refunded). The current state = replay of all events. Every cent is accounted for. Regulators love this. This is how real banks work.

Rate Limiter
API throttling · DDoS protection · Fair use quotas
INFRA HIGH SPEED
1Step-by-Step Data Flow
1
Where to Put the Rate Limiter
Rate limiting should happen at the edge, before requests reach app servers. Options: (1) API Gateway layer (AWS API Gateway, Kong). (2) NGINX middleware. (3) Application code (last resort). Edge enforcement means blocked requests never consume application resources. Rate limit by: API key, user_id, IP address, or combinations.
2
Token Bucket Algorithm (Best for most APIs)
Each user has a "bucket" with capacity N tokens. Tokens refill at a fixed rate (e.g., 100 tokens/minute). Each request consumes 1 token. If bucket has tokens → allow. If bucket empty → reject with HTTP 429. Implementation in Redis: INCR user:{id}:tokens on refill timer, DECR on each request. Allows bursts up to bucket capacity — perfect for APIs where legitimate users sometimes spike.
Redis INCR/DECR
3
Sliding Window Counter (Best accuracy)
Divide time into 1-second sub-windows. For a "100 requests/minute" limit: maintain a Redis counter for each second for the past 60 seconds. Sum of all 60 counters = request count in the sliding window. If sum <100 → allow and increment current-second counter. This is more accurate than fixed window but slightly more complex. Implementation: Redis sorted set of timestamps, or per-second hash keys with TTL.
Redis Sorted Set
4
Distributed Rate Limiting
With multiple servers, local in-memory counters don't work — each server sees only its own traffic. Solution: use a centralized Redis cluster as the shared state. All servers increment/check the SAME Redis key. For ultra-high throughput, use a Lua script in Redis to make the check+increment atomic: no race conditions even at 1M requests/sec.
Redis Lua Script

Collaborative Docs
e.g. Google Docs · Notion · Figma · Miro
REAL-TIME CRDT CONFLICT RESOLVE
1The Core Problem

The Challenge

  • User A and User B edit the same line simultaneously
  • Both see "Hello World" initially
  • A changes it to "Hello Alice"
  • B changes it to "Hello Bob"
  • What should both see after sync?
  • Both edits must merge without data loss

Non-Functional

  • Edits propagated in <100ms
  • 100 concurrent editors per document
  • Offline editing supported
  • Full version history
  • Works even on bad networks
2Step-by-Step Data Flow
1
User Opens Document — Joins a Room
User opens the document URL. Client establishes a WebSocket connection to a Document Server for that doc_id. Server adds user to the document "room." Current document state is fetched from PostgreSQL (latest snapshot) and sent to the client. Other users in the room are notified of the new presence. Cursor position registered in Redis.
2
User Types — Operation Generated
Every keystroke generates an operation: {type: "insert", position: 42, char: "A", user_id: "U1", timestamp: T1}. The client applies the operation locally FIRST (optimistic update — user sees their own typing immediately). Then sends the operation to the server. This is why collaborative editors feel snappy — you never wait for round-trip confirmation to see your own keystrokes.
3
Conflict Resolution — OT or CRDT
Operational Transformation (OT): When two operations conflict (same position), transform one relative to the other. Example: A inserts at position 5, B deletes at position 5. When A's operation arrives at B's client after B's delete, OT adjusts A's position to account for B's deletion. Google Docs uses OT — requires a central server to order operations. CRDT: Each character gets a globally unique ID. Merging is mathematically guaranteed to converge. No central ordering needed. Figma uses CRDTs. Modern approach, more complex to implement.
OTCRDT
4
Broadcasting to Other Editors
Server receives operation from User A, applies OT/CRDT to resolve conflicts, then broadcasts the transformed operation to all other users in the document room via WebSocket. Each client applies the received operation to their local document state. The document converges to the same state on all clients. Operations are also appended to a log in Cassandra for version history.
WebSocket BroadcastCassandra Log
5
Persistence and Snapshots
Don't save the document on every keystroke — that's thousands of DB writes/minute. Instead: buffer operations in memory, auto-save a full document snapshot to PostgreSQL every 30 seconds. Keep the operation log in Cassandra. Version history = list of snapshots + the operations between snapshots. To restore to any point in time: load the nearest snapshot + replay operations up to that timestamp.
PostgreSQL SnapshotCassandra Ops Log
3Interview Gold 🏆
⚡ Say These in Your Interview
!
OT requires central server, CRDT doesn't: OT works because the server sees ALL operations in a total order. CRDT works peer-to-peer because the merge is deterministic regardless of order. For Google Docs-style (server-authoritative), OT is fine. For Figma-style (offline-first, P2P), use CRDT.
!
Presence indicators: "Sarah is editing line 42" — cursor positions stored in Redis with 5-second TTL (updated on each cursor move). When TTL expires, user's cursor disappears. Broadcast cursor updates via WebSocket. DO NOT save cursors to PostgreSQL — they're purely ephemeral.
!
Why snapshots + operation log?: Replaying 1M operations to reconstruct a document from scratch takes too long. Take periodic snapshots so you only replay the last N operations. This is the classic write-ahead log + checkpoint pattern (same idea as PostgreSQL itself uses internally).

Recommendation Engine
e.g. Netflix · Amazon · Spotify · YouTube algorithm
DATA SCALE ML PIPELINE
1Step-by-Step Data Flow
1
Collecting Behavioral Signals
Every user action is a signal: watched 80% of a video, clicked a product, added to cart, skipped a song. These events stream into Kafka in real-time: {user_id, item_id, action, timestamp}. A Spark Streaming job consumes Kafka and maintains a rolling feature vector per user: "User U1 likes: action movies, sci-fi, 90-minute films."
KafkaSpark Streaming
2
Offline Training — Matrix Factorization
Daily batch job in Spark trains a model on all historical interactions (stored in Snowflake). The model: a user-item interaction matrix (rows=users, cols=items, value=rating/interaction). Matrix Factorization decomposes this into two smaller matrices: a User embedding matrix and an Item embedding matrix. Each user and item gets a vector of 100 numbers representing their "taste DNA." Similar users → similar vectors.
Spark ALSSnowflake
3
Storing Embeddings in Vector DB
All item and user embeddings (100-dimensional vectors) are stored in a Vector Database (Pinecone or pgvector). To find recommendations for User A: fetch User A's embedding vector, query the vector DB for the top-K item vectors with smallest cosine distance. These are the most similar items. This is Approximate Nearest Neighbor (ANN) search. Retrieves 1000 candidates in milliseconds across millions of items.
Pinecone / pgvectorANN Search
4
Two-Stage Recommendation
Stage 1 — Retrieval: Vector DB returns top 1000 candidate items from millions (recall). Fast but not super accurate. Stage 2 — Ranking: A more complex ML model scores each of the 1000 candidates using rich features (time of day, device, recent context, diversity). Returns top 20 for display. This two-stage approach is used by Netflix, YouTube, Spotify. Stage 1 runs in <50ms, Stage 2 in <100ms.
5
Serving and Caching Results
Precompute recommendations for every active user during off-peak hours. Store the top-50 recommendations per user in Redis. When user opens the app, recommendations are retrieved from Redis in milliseconds — no model inference needed. Refresh the cache every 30 minutes or on significant new behavior. Cold-start (new user): serve trending/popular items until enough data collected.
Redis Cache

⚡ Say These in Your Interview
!
Collaborative Filtering vs Content-Based: CF: "Users who liked X also liked Y." Problem: cold start (no data on new items). Content-based: "This item has features similar to what you liked." Problem: filter bubble (never discovers new types). Netflix uses hybrid — both together.

Why precompute?: Running ANN search + ranking model at request time for every user = expensive. For 100M users all logging in at morning, that's 100M inference calls simultaneously. Precompute at night when traffic is low, serve from Redis at peak time. Trade freshness for latency and cost.

Diversity injection: Pure ML recommendations would show 10 variations of the same thing (10 action movies). Deliberately inject diversity: enforce max 2 items per category, add random exploration (10% of results are random items to gather new signal). This is the explore vs exploit tradeoff.

Distributed Cache System
Redis Cluster · Memcached · CDN design · Cache strategies
INFRA LOW LATENCY
1Step-by-Step Data Flow
1
Cache-Aside Pattern (Most Common)
Application checks cache FIRST. Cache HIT: return data from Redis (~1ms). Cache MISS: fetch from DB (~100ms), store in Redis with TTL, return data. Application is responsible for all cache interactions. The cache is a lazy cache — only populated when first requested. Simple, flexible, most widely used pattern. Works well when reads >> writes.
Redis GETRedis SET with EX
2
Write-Through Pattern
Every write goes to BOTH the cache and the DB simultaneously. Cache is always consistent with DB. Reads always hit cache. Downside: write latency increases (must wait for both). Useful when data is read immediately after being written (e.g., user profile update → immediately shown to the user). But wastes cache space on items that are written but never read again.
3
Horizontal Scaling — Consistent Hashing
When you have 3 Redis nodes, how do you decide which node stores key "user:123"? Naive approach: hash(key) % 3. Problem: adding a 4th node → % 4 → almost every key remaps → massive cache miss storm. Consistent hashing: arrange nodes on a virtual ring. Key maps to the first node clockwise. Adding a node only remaps ~1/N keys. Redis Cluster uses this internally with 16,384 hash slots.
Redis ClusterConsistent Hash
4
Cache Eviction Policies
LRU (Least Recently Used): evict keys not accessed recently. Best for general-purpose caches. LFU (Least Frequently Used): evict keys accessed least often overall. Better for workloads with stable hot keys. TTL-based: set an explicit expiry on each key. Guaranteed freshness. Most production systems combine: set a TTL AND use LRU within TTL'd keys. Redis supports all policies via maxmemory-policy config.
5
Common Cache Failure Patterns
Cache Stampede: Popular key expires → 10K requests all miss simultaneously → DB gets hammered. Fix: use a mutex lock on cache miss (first request fetches from DB, others wait). Or use probabilistic early expiry — randomly refresh before expiry. Cache Penetration: Requests for keys that will never exist (user:9999999) bypass cache every time. Fix: cache null results with short TTL, or use a Bloom Filter at the door. Cache Avalanche: All keys expire at the same time. Fix: add random jitter to TTL values.

Cache stampede is the most common cache failure: "We had a major outage when our cache expired and 100K requests hit the DB simultaneously." Showing you know this problem and its solution (mutex + probabilistic refresh) immediately marks you as experienced.
!
Bloom Filter for cache penetration: A Bloom Filter is a probabilistic data structure. "Is user_id=99999 in our system?" Bloom says NO → skip DB entirely. Bloom says YES → might be in DB (small false positive rate), check DB. 0% false negatives. Uses 10x less memory than a hash set for the same data.
!
What to cache? Cache what's: (1) expensive to compute, (2) read frequently, (3) changes infrequently, (4) OK to be slightly stale. Don't cache: financial balances (must be exact), session security tokens (must be invalidated instantly), user-generated content that changes every second.
!
Hot key problem: One Redis key gets 1M requests/sec (a celebrity's profile). Single Redis node can't handle it. Solutions: local in-process cache on each app server (100ms TTL), or replicate hot keys to multiple Redis nodes and randomly pick one (load spread).
